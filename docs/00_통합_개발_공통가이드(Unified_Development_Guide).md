# BEST 통합 개발자 공통 가이드 및 작업지시서 (Unified Development Guide)

**문서 목적:**
BestClubVN(통합 플랫폼), BestERP(가맹점 SaaS), 대한김치(가맹점 샘플) 세 웹사이트를 독립 배포·운영하되, 공통 데이터 규격과 API로 연결합니다. BestERP에 한 번 등록한 가맹점 상품이 가맹점 홈페이지와 BestClubVN 통합 쇼핑몰에 자동 노출되어 실제 주문·구매까지 이어지도록 개발 기준 및 코딩 표준을 통합합니다.

---

## 1. 프론트엔드/백엔드 코딩 표준 (Harness Rules)

### 1.1. 기술 스택 (Tech Stack)
*   **Frontend**: HTML5, Vanilla JavaScript (ESM 모듈), CSS3 (Tailwind 지양, Custom Vanilla CSS 선호)
*   **Build Tool**: Vite (로컬 개발 서버 및 빌드 병합용)
*   **Backend / Database**: Firebase v10 SDK (Auth, Firestore, Storage)

### 1.2. 시스템 제어 및 보안 규칙
1.  **인코딩 철칙 (UTF-8)**: Windows PowerShell 스크립트 텍스트 조작 지양. 대규모 텍스트 처리 시 Node.js 환경 등을 이용하여 한글 인코딩을 보호.
2.  **보안 (Global Auth Guard)**: 신규 HTML 페이지 추가 시 `<script type="module">` 블록에 `checkAdminAuth()` 등 권한 검증 로직을 기본 탑재하여 인가되지 않은 접근을 리다이렉팅.
3.  **스타일링 원칙 (UI/UX Aesthetics)**: 폰트는 구글 폰트(Inter 등 웹폰트) 고정 적용. Glassmorphism, Micro-animations 등 고급스러운 룩앤필(Premium Feel)을 유지.
4.  **Firebase 모듈화**: 기능별 리포지토리 패턴 권장(`services/` 폴더 내 API/DB 래퍼 구현). CDN 하드코딩을 지양하고 모형화된 모듈을 사용.
5.  **소스 복구 및 롤백 주의 사항**: 장애 발생으로 롤백 전, 현재 작업 중인 `uncommitted changes` (AI 생성 코드 등)가 유실되지 않도록 철저한 확인/백업 필수.

---

## 2. 전체 시스템 목표와 플랫폼별 역할 및 통제

*   **BestClubVN**: 통합 플랫폼 및 공통 정책 기준 (통합 회원 ID, 가맹점 ID, 회원-가맹점 관계, 포인트 원장, 보너스 티켓·정책, 공통 API, 통합 쇼핑몰 `/mall.html`)
*   **BestERP**: 가맹점별 SaaS CRM·ERP·AI 경영지원 및 상품 카탈로그 (상품·메뉴·서비스 등록, 가격·옵션·판매 상태 관리, 매출 분석)
*   **가맹점 홈페이지 (예: 대한김치)**: 고객용 판매·서비스 화면 (BestERP에서 공개한 해당 가맹점 상품 표시, 상세 조회, 장바구니, 주문·예약 접수)
*   **핵심 원칙**: 상품 정보는 **BestERP에서 단일 기준**으로 관리. 회원·가맹점·포인트·보너스 티켓 관리는 **BestClubVN 규격**을 따름. 주문결제 재고 관련 데이터 덮어쓰기 절대 금지.

## 3. 강력 통제 및 필수 지시 사항 (CRITICAL)

### 🚨 [CRITICAL] 권한(Role) 부여 네이밍 규칙: 'CEO' 통일
앞으로 온보딩되는 **모든 가맹점 주(Merchant Owner)**에게 시스템 권한을 부여할 때, `ADMIN`이나 `admin` 등 파편화된 명칭을 절대 사용하지 마십시오.
1.  관리자 권한은 백엔드(Firestore Users Collection) 및 Custom Claims에서 반드시 대문자 **`CEO`** 로 통일해야 합니다.
2.  `SUPER_ADMIN` (개발사/본사)을 제외한 모든 가맹점 대표는 `CEO` 롤을 통해 각자 가맹점 리소스에 접근합니다.
3.  스케일업 대비 DB 상 부여되는 Role 명칭 관리에 절대적으로 주의를 기울이십시오. (향후 수백 개 가맹점 대비 구조화)

### 🚨 [CRITICAL] Firestore 보안 규칙 (Rules) 사전 검증 의무화
새로운 컬렉션을 추가하거나, 백엔드 로직(수정/생성/삭제)을 개발한 이후에는 반드시 **클라이언트 단에서 `Missing or insufficient permissions` 에러가 발생하지 않는지 사전 검증해야 합니다.**
1.  **신규 컬렉션 생성 시:** `firestore.rules`에 해당 `match` 블록이 누락되었는지 확인하고 반드시 룰을 추가 배포(`firebase deploy --only firestore:rules`)합니다.
2.  **권한 계층 분리 시:** User, Admin, SuperAdmin, Merchant 각 역할(Role)이 `create`, `update`, `delete`, `read` 오퍼레이션에서 차단당하지 않는지 Rule 시뮬레이터를 돌리거나 실제 계정으로 통과를 확인합니다.
3.  동일한 권한 에러를 반복하여 발생시켜 고객(클라이언트) 화면에 표출되는 것은 **용납되지 않는 엄중한 결함**으로 간주합니다.

## 4. 핵심 사용자 업무 흐름

1.  가맹점 관리자가 **BestERP**에 로그인하여 상품/서비스 정보를 등록.
2.  상품을 `draft`(임시저장) 또는 `published`(판매 공개) 상태로 전환.
3.  공개 상품은 해당 **가맹점 홈페이지**와 **BestClubVN `/mall.html`** 에 API를 통하여 자동 노출됨.
4.  고객이 화면 확인 후 장바구니에 담아 주문/예약 신청.
5.  서버가 처리 시 상품 공개 상태, 가격, 옵션, 재고 여부를 무조건 **즉시 재검증** (클라이언트 측 단가 신뢰 불가).
6.  결제 결과 기록은 기준 결제 서버/스냅샷을 참고하여 원자적 처리 후, 결과 통계를 **BestERP** 매출/CRM에 반영.
7.  주문 조건 충족 시 **BestClubVN** 승인된 정책/API를 통해 포인트(Point/BM/Ticket) 멱등성 보장 처리.

## 5. 공통 서비스별 요구사항 및 정책

### 5.1. 상품 카탈로그 규격
*   **지원 상품 유형**: 메뉴(`menu`), 일반 실물 상품(`physical_product`), 서비스(`service`), 예약형 상품·서비스(`booking`)
*   **공통 상품 필드 (최소 권장)**: `product_id`, `merchant_id`, `category_id`, `product_type`, `product_name`, `description`, `images`, `price`, `currency`, `sale_status`, `options`, `unit`, `SKU`, `inventory`, `shipping_rules`, `booking_rules`, `display_order`, 생성/수정/공개 시간, `source_system` 등
*   **상품 상태 정책**: `draft` (임시저장), `published` (판매 공개), `paused` (일시 중지), `sold_out` (품절), `archived` (판매 종료)

### 5.2. BestClubVN `/mall.html` 통합 쇼핑몰 요구사항
*   **상품 수집**: HTML 긁어오기 식(Scraping) 크롤링 배제, ERP가 제공하는 공통 상품 조회 REST/DB API 호출.
*   **장바구니 로직**: 다중 가맹점 통합결제 허용 범위와 처리 기준에 맞춰 정책 수립.
*   **서버 재검증 (중요)**: 고객 브라우저에서 요청한 품목 가격 정보를 절대 신뢰하지 않고, **서버에서 DB를 100% 재검증**하여 최종 결제 단가 처리.

### 5.3. 가맹점별 홈페이지 연동 (예: 대한김치)
*   상품별 웹 코드를 직접 수정하는 낡은 방식 금지.
*   UI 상에서 API/DB를 쿼리하여 무조건 자동 동기화.
*   각 홈페이지는 사전에 할당받은 `merchant_id`만 쿼리 조건으로 필터하여 **타 가맹점 데이터 엿보기를 철저히 차단(Firestore Rule 포함).**

### 5.4. 주문·결제·재고 등 멱등성 및 원자적 처리
*   주문 생성 시점의 모든 조건(상품 가격 정보 및 옵션) 스냅샷(Snapshot)으로 고정 및 영구 복제 저장.
*   결제 시스템, 재고 차감 시 멱등성을 보장하며, 다중 트랜잭션 충돌 방지 로직 적용.
*   포인트 잔액 임의 수정은 금지되며, 반드시 트랜잭션 기록-원장 계산 방식을 통해 도출 (API 타임아웃 대비 재처리 로직 추가 구성).

### 5.5. 보안·개인정보·테넌트 분리 방침
*   가맹점 간(Tenant 멀티플랫폼) 데이터 분리 아키텍처 철저 확립(Role: CEO 관리).
*   모든 로직에서 감사 로그(Audit Logs) 활성화 기본.

### 5.6. BestERP AI 경영지원 범위
*   단순 CRM, 자재 관리를 넘어 **AI 경영지원**(업무 보고 요약, 지연업무 발견, 타겟 광고 제안 등) 도입.
*   **모든 AI에 의한 데이터 DB 자체 조작(CRUD)**은 반드시 직원이 사전 승인한 후에만 Trigger 될 수 있도록 제어.

## 6. 통합 검수 체크리스트 (0/17)

- [ ] 가맹점 A가 BestERP에 상품·가격·이미지를 등록하고 저장한다.
- [ ] 상품을 공개하면 A 홈페이지와 BestClubVN `/mall.html`에 시간 내 표시된다.
- [ ] 가맹점 B 상품은 A 홈페이지에 노출되지 않는다.
- [ ] mall.html에서 전체 가맹점 상품, 가맹점 분류/정렬이 작동한다.
- [ ] 상품명·가격·옵션 변경이 모든 연결 화면에 반영된다.
- [ ] 임시저장/종료 상품은 공개 안 됨, 품절은 구매 차단.
- [ ] 옵션 등에 따라 서버가 최종 금액을 정확히 재계산한다.
- [ ] 재고 부족·동시·중복 주문/결제가 원자적으로 차단/완료된다.
- [ ] 결제 승인 전이가 올바르다.
- [ ] 배송 정보가 ERP에 올바르게 전달된다.
- [ ] 포인트·보너스 티켓이 한 번만 처리(멱등성)된다.
- [ ] 예약 서비스의 시간 충돌 취소가 올바르게 돌아간다.
- [ ] 데이터가 BestERP AI 보고서에 반영된다.
- [ ] 모바일/다국어 지원 정상이다.
- [ ] 테넌트 해킹/엿보기가 서버 차단된다.
- [ ] 타임아웃 등 재처리와 로그가 동작한다.
- [ ] 기존 사이트 회귀/롤백 테스트 통과.

## 7. 개발자별 담당 범위 및 협업 지시문 (대표 통첩)

**"BestClubVN, BestERP, 대한김치는 독립 배포되지만 하나의 묶음 플랫폼입니다! 본인의 화면만 만들지 말고 전체 데이터의 흐름과 보안 상태를 우선하세요!"**

*   **기준 원칙**: 상품 등록은 무조건 BestERP / 포인트·티켓은 무조건 BestClubVN.
*   **사전 설계 문서화**: 모든 개발자는 개발 착수 전, 본인의 수정 계획과 공통 API 약속을 정리하여 관련 문서에 남기고, 승인을 얻은 뒤 실제 코딩(Production)에 도입하시기 바랍니다.

### 담당 부문:
*   **개발자 A (BestClubVN)**: 통합 ID 관리, 쇼핑몰 인프라, 권한 부여 기반, 포인트 API.
*   **개발자 B (BestERP)**: 테넌트 분리, ERP 모듈 고도화, 상태 조회용 통합 API 구현 및 데이터 상태 변환 로직.
*   **개발자 C (가맹점 홈 / 대한김치 샘플)**: 기존 정적/하드코딩 방식 제거 후 BestERP 상품 DB 연동화, 단일 결제 모듈 연동 재정립.
